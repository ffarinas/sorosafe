# SoroSafe Soroban v1 — security model and validation

Status: implemented and exercised on Stellar Testnet. **Not independently audited. No SoroSafe factory has been deployed to Mainnet.** The use of audited dependencies does not make this composition audited or invulnerable. This document describes the current source and published artifacts; the dated evidence below records earlier validation runs.

## Custody and authorization

Each vault is an immutable WASM contract with a permanent C-address. The factory has no administrator, withdrawal function, upgrade function, or mutable fee configuration. Creating a vault requires the creator's Stellar authorization, includes all constructor arguments, and namespaces the deployment salt by creator. The factory explicitly authorizes only the predicted vault constructor with the exact arguments. There is no post-deployment initialization window.

The vault accepts 1–20 distinct G-account signers and a quorum of 1–N; a vault may start with its creator alone and add signers through a ChangeRules proposal. Proposing counts as the proposer's approval. `propose` or `approve` executes when it reaches quorum and the action is fundable. If a payment lacks funds for its amount and fee, the request and approval remain pending for later execution. Signers are authorized using Soroban `Address.require_auth`, which delegates signature verification and transaction replay prevention to Stellar. SoroSafe does not implement a signature scheme. A compromised signer cannot spend below quorum; a 1-of-1 vault has no protection against compromise of its sole signer. A quorum can change all signers and the threshold, including replacing the original creator, without changing the vault's address.

Stellar's native multisig also supports signer rotation while retaining the account address, including disabling the original master key. A contract is not inherently safer than a correctly configured native multisig. SoroSafe uses a contract to enforce its proposal lifecycle, shared approval rules and service-fee accounting. In either model, a compromised key counts toward the configured quorum; obtaining the remaining valid approvals can authorize a payment.

Proposals, approvals and a cumulative confirmed-payment count per recipient are stored on-chain, not in D1. Proposal IDs are monotonically increasing; creation requires the expected next ID. Each proposal binds its action, proposer, expiration (at most seven days) and rules epoch. An approval is counted once per signer. A signer can revoke their own approval. Only the proposer can cancel their pending proposal. Terminal and expired proposals cannot execute. Changing the rules increments the epoch and invalidates older pending proposals. Execution is permissionless once the current quorum has approved, so a different wallet can pay the network fee.

## Transfers and fees

Only built-in Stellar Asset Contracts in the immutable factory asset list are supported. No arbitrary contract calls, allowances, external signature policies, `__check_auth` bypass, staking plugins, or code upgrades are exposed. Executing a payment transfers its exact amount to its recipient and atomically records its service fee as `fees_owed` in the same token. The fee stays reserved in the vault until collected; it is not transferred to the collector during the payment. The service fee uses OpenZeppelin's full-precision `mul_div_ceil(amount, bps, 10000)`; amounts plus fees are checked for overflow and against the SAC transfer limit. Fractional smallest units round upward. The fee ceiling is 1,000 basis points; it is a validation bound, not the deployed rate of 25 basis points (0.25%).

The execution state is consumed before the recipient transfer. A failed transfer or fee-accounting update rolls back the entire operation. A payment requires a balance covering its amount, its new fee and all previously accrued fees; reserved fees cannot fund another team payment. `claim_fees` is permissionless but can send only the accrued balance for an asset to the fixed collector. A failed collection rolls back its accounting change and leaves the fees owed. A direct request to the SAC to transfer from the vault cannot authenticate the vault. There is no alternative generic execution or allowance path that bypasses the fee.

A nonzero-fee factory deployment checks that the collector can receive each asset. **A missing or frozen collector trustline blocks fee collection, not team payments.** Maintaining that account remains an operational dependency for collecting revenue. The collector and fee are deliberately immutable; there is no collector-rotation path. Issuer restrictions on the vault or recipient, clawback of vault funds, or a recipient that cannot receive the asset can still prevent payments. Unsupported tokens accidentally deposited into the vault have no withdrawal path in v1: the asset list must be reviewed before funding.

## Libraries and reproducibility

- Soroban SDK `=26.1.1` with its official dependency-constraint fix; Stellar host handles authorization and SAC transfers.
- OpenZeppelin `stellar-contract-utils` v0.7.2, exact revision `a9c42169000638da937577f592ebf61a7a3c94ca`. Used for the fee arithmetic. The generic smart-account framework is not used: exposing generic calls would add a fee bypass surface here.
- OpenZeppelin's v0.7.0 audit includes the fixed-point mathematics modules. This is evidence of component review, **not evidence that SoroSafe or every change through v0.7.2 is audited or independently verified in production**.
- `contracts/Cargo.lock` is committed. Release builds enable overflow checks, use one codegen unit and LTO, and contain no debugging symbols. Build with `stellar contract build --locked` (CLI 25.2.0 or compatible; Rust 1.94.1 used for these artifacts).
- Published WASM hashes are in `lib/contract-artifacts.json`. Before enabling a vault, the client checks both vault and factory WASM bytes against those hashes and checks the factory registration. A self-reported factory address alone is insufficient.
- The committed RustSec snapshot (`docs/contract-dependency-audit.json`, advisory database dated September 28, 2026) reports zero known vulnerabilities and informational `RUSTSEC-2024-0436` for the unmaintained `paste` dependency in the native test host. This is a historical dependency check, not a current audit. The prior target-specific dependency check found `paste` absent from the deployed WASM dependency tree.

## Backend independence and application boundaries

`/contract?network=testnet&address=C…` reads configuration, balances, proposals and approvals from Stellar RPC and constructs wallet-signed operations locally. The contract does not call SoroSafe's backend. D1 still supplies invitation links, human names and private shared contacts for the normal onboarding path; these are collaboration data, not custody authority. Losing that service does not prevent a signer from using the contract or another client. RPC availability remains necessary.

Tokens retain their network, code and issuer and are resolved to their deterministic SAC IDs. Payment preparation and approval validate the actual contract/function/arguments before requesting a wallet signature. There is no XLM fallback. Recipient preflight checks reduce avoidable failures but cannot guarantee execution: account, trustline or issuer authorization state can change before submission. A failing recipient transfer also rolls back the approval that attempted automatic execution. The UI shows token-specific service fees and XLM network costs separately. Only known catalog assets are displayed. The independent route supports a matching SoroSafe code deployment with any valid fee configuration; users must still confirm the address and fee with their team.

Configuration and accrued fees use instance storage; proposals, payment counts and factory registration use persistent storage. Contract calls extend the TTL of entries they touch toward 30 days when below the configured threshold; they do not renew every historical entry. Read simulations do not themselves renew ledger TTL. Archived data is recoverable, not reset; the operator must keep instances/code/proposal storage live or restore archived entries through Stellar tooling. The first version does not yet provide a dedicated manual restoration interface. A malicious RPC or frontend can mislead users; the contract enforces the quorum, but it cannot protect a quorum that signs a malicious, correctly authorized payment. Hardware-wallet and clear-signing coverage remain to be verified device by device.

## Evidence and limits

The following summarizes committed evidence and previously reported results. Updating this document did not rerun live Testnet workflows, deploy contracts or move funds.

- 35 Rust tests are present (28 vault, 5 factory, 2 faucet), with the prior passing result recorded in the README. Coverage includes quorum and authorization, pending unfunded payments, fee accrual and permissionless collection, reserved-fee exclusion, frozen/missing collector trustlines, atomic rollback, signer rotation and factory provenance/namespacing.
- 21 real-Testnet workflow checks recorded on October 6, 2026 in `docs/soroban-testnet-evidence.json`, using compiled WASM, Friendbot-funded ephemeral wallets and real Ed25519 transaction signatures. They include fee accrual and subsequent collection. Negative preflight checks exercise contract simulation; the invalid transaction-signature check is submitted to RPC. Positive operations have transaction receipts. The recorded vault and factory hashes match `lib/contract-artifacts.json`; the test fixture uses a different factory address from the public demo. Test secrets were never persisted.
- 19 application onboarding checks recorded on October 6, 2026 in `docs/contracts-onboarding-evidence.json`: SEP-10 sessions, shared invitations, exact constructor validation, activation, shared contacts and rejection of memo-dependent destinations.
- The README reports 36 backend regression checks and passing client transaction-encoding checks, including 1–20 signers, threshold 1–N, exact asset, recipient, function and constructor encoding. These are separate from the dated on-chain evidence.
- TypeScript, ESLint, Rust Clippy and production build checks were reported during prior validation; this documentation update is not a new validation record for them.
- Mainnet read-only RPC checks dated September 29, 2026 record the XLM/USDC/USDT0 SAC addresses and seven decimal places (`docs/mainnet-sac-readonly-evidence.json`); no Mainnet token transfers were submitted.
- Prior browser checks read the Testnet vault balance and completed payment/rotation history. These do not constitute a complete Freighter hardware-wallet signing test.

Pending before production custody: independent review of this exact WASM and application signing flow, monitoring and operations for fee collection, a decision on unsupported-asset recovery, storage-restoration operations, real Freighter/device coverage, and a controlled Mainnet exercise with the chosen fee recipient and approved small amounts. The current implementation supports basic payments; email/passkeys, batches, staking and arbitrary dApp execution are outside v1.
